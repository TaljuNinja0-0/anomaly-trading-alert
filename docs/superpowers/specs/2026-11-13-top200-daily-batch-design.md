# 설계: 이상매매 탐지 실서비스 확장 (시가총액 상위 200, 일봉 배치)

> 이 문서는 **설계 문서**다. 구현은 사용자가 이 문서를 읽고 승인한 뒤,
> 별도 요청으로 writing-plans → 실제 구현 순서로 진행한다. 이번 산출물은
> 설계까지다.

## 의도와 배경

토이 프로젝트(`anomaly-trading-alert`, 종목 5개 과거 데이터)에서 4단계
로드맵(통계룰→ML→DL→파운데이션모델)과 앙상블을 검증했고, 결론은
`docs/findings.md`에 정리돼 있다: **ML(IsolationForest)이 5/5 탐지로
명확한 최고 성능**이고, 앙상블은 구조적으로 이득이 없었다.

사용자 지시: 토이 프로젝트와 같은 방식(일봉 기준)을 그대로 유지하고,
가장 잘 나온 안(ML)을 골라서 시가총액 상위 200개 종목으로 확장한다.
단, 지금은 설계만 하고, 실제로 시도해본 뒤 성능을 보고 그 다음(분봉
전환 등)을 판단한다 — 즉 이 설계는 "완성형 서비스"가 아니라 **"일봉+ML을
200종목에 적용하면 실제로 어떤지 보기 위한 최소 버전"**이다.

## 목표 / 비목표 / 안티골

**목표**
- 시가총액 상위 200종목을 매일 1회(장마감 후) 동적으로 갱신해서 추적
- 200종목 전체에 ML(IsolationForest) 이상탐지를 매일 1회 실행
- "오늘 어떤 종목이 이상치로 판정됐는지"를 조회 가능한 형태로 저장
- 토이 프로젝트 코드(`kis_client`, `ml_detector`)를 최대한 재사용

**비목표(이번 범위 아님)**
- 실시간/분봉 기반 탐지 — 보류. KIS 과거 분봉 조회(`FHKST03010230`)가
  약 11개월까지만 보관된다는 건 이번 대화에서 실제 호출로 확인했지만,
  "분봉으로 가는 게 일봉보다 실제로 나은가"는 아직 검증 안 함 — 이번
  확장 결과를 본 뒤에 판단
- 알림 발송(이메일/푸시/슬랙 등) — 결과를 저장·조회 가능하게만 하고,
  발송 채널은 다음 단계
- 매수/매도 추천, 자동매매 — 기획서 원칙 그대로 유지
- 웹 대시보드/UI — 이번 범위는 백엔드 파이프라인 + 결과 저장까지

**안티골(이러면 실패)**
- KIS API 레이트리밋에 걸려 200종목을 장마감 후 합리적 시간 안에 다
  못 돌리면 실패
- 매일 수동 개입이 필요하면(진짜 "배치"가 아니면) 실패

## 제약

- KIS 기간별시세조회는 1콜당 ~100행 cap — `kis_client.get_daily_price`가
  이미 페이지네이션 처리 중(90일 단위 청크). 200종목 x 페이지네이션이면
  호출 수가 꽤 늘어남 — 실측 필요(아래 "성능 추정" 참고).
- KIS 토큰 발급은 1분당 1회 제한 — 이미 알고 있는 제약, 토큰은 배치
  시작 시 1회만 발급해서 재사용.
- ML 단계는 베이스라인 100행이 전부 non-NaN이어야 "ok" — 신규상장·
  거래정지 종목 등은 `insufficient_data`로 빠지는 게 정상 동작.
- `contamination=0.05`, `ML_BASELINE_LOOKBACK=100`은 5개 종목 기준으로
  튜닝한 값 — 200종목에 그대로 쓰면 종목별 변동성 차이로 과탐/과소탐
  편차가 날 수 있음. 이번 라운드는 이 값 그대로 쓰고, 결과를 보고
  필요하면 재튜닝(다음 단계).

## 접근 방식

1. **(추천) 기존 `anomaly-trading-alert` 레포 확장.** 유니버스
   산출·전종목 스캔 모듈을 추가하고, 검증된 `kis_client`/`ml_detector`를
   그대로 재사용. 장점: 가장 빠르고 리스크가 적음(이미 테스트된 코드).
   단점: "토이 PoC"와 "실서비스 성격 코드"가 한 레포에 섞임 — 나중에
   분리할 수도 있음.
2. **새 레포 생성.** 장점: 성격이 처음부터 명확히 나뉨. 단점: 검증된
   모듈을 복붙/패키지화해야 하는 비용 — "일단 시도해보고 성능 본다"는
   지금 단계엔 과함.
3. **기존 캡스톤 레포(`AI_Gentle_Viking_RE`)에 통합.** 캡스톤은 배포
   중단 상태(메모리: `deployment_status.md`)라 성격이 다른 프로젝트를
   얹는 건 부적절 — 제외.

**추천: 1번.** "먼저 시도해보고 성능 본다"는 목적에 가장 빠르고,
토이 프로젝트의 테스트·코드가 그대로 재사용된다. 나중에 정말 서비스로
간다면 그때 분리해도 손해가 크지 않다 — 모듈이 이미 독립적으로 잘
나뉘어 있다(`kis_client`/`detector`/`ml_detector` 등).

## 데이터 / 저장 설계

- **유니버스**: KIS API의 "국내주식 순위분석 — 시가총액 상위" 조회로
  **코스피+코스닥 통합** top-200 종목코드를 매일 1회 가져온다(기획서
  "고정 KOSPI200 대신 매번 재계산" 취지 — 코스피 한정이 아니라 "개인
  투자자가 시간이 없어 상시 감시 못 하는 종목" 전체를 포괄하는 쪽으로
  해석해 통합으로 결정함). 정확한 TR_ID/파라미터는 토이 프로젝트에서
  써본 적 없는 엔드포인트라 구현 시 확인 필요(남은 질문 참고).
  **리스크**: 코스닥 종목은 코스피 대형주보다 변동성이 구조적으로 커서,
  5개 코스피 대형주로 튜닝한 `contamination=0.05`/`ML_BASELINE_LOOKBACK=100`이
  코스닥 종목에는 과탐으로 작동할 가능성이 있다 — 1차 실행 결과를 보고
  시장별로 파라미터를 분리할지 판단한다(이번 설계 범위 밖, 다음 단계).
- **저장소**: SQLite 파일 하나(`universe_scan.db`)로 시작. 200종목 x
  매일 1회 수준이면 Postgres 같은 운영 DB는 과하고, 설치·운영 부담 없이
  파일 하나로 충분하다. 스키마(제안):
  - `scan_runs(run_date, started_at, universe_size, elapsed_seconds)`
  - `scan_results(run_date, ticker, name, status, is_anomaly, anomaly_score)`
- **실행 방식**: cron 1개, 매일 **17:00 KST**(장마감 15:30 + 1.5시간
  여유). 실행 호스트는 이 환경(`/home/user`)으로 가정 — 캡스톤 때도
  같은 환경에서 `collector_kis.py` 등 크론이 몇 달간 안정적으로
  돌았던 전례가 있다(빌더 체크에서 지적된 질문, 내 판단으로 결정).
  **데이터 발행 지연 대응**: KIS 일봉 데이터가 장마감 직후 바로
  집계되는지, 지연이 있는지 토이 프로젝트에서 검증한 적이 없다(항상
  과거 확정된 구간만 조회했음). 16:00 정각 대신 17:00으로 여유를
  두는 것과 별개로, 파이프라인 자체에 **최신성 체크**를 넣는다 —
  조회된 데이터의 마지막 날짜가 오늘 날짜와 다르면 "아직 집계 안 됨"으로
  보고 해당 종목을 건너뛰고 로그만 남긴다(에러로 죽지 않음, 다음날
  배치에서 자연히 따라잡음).

## 분석 로직 재정의 — 토이 프로젝트와 다른 핵심 지점

토이 프로젝트의 `run_case_ml`은 "지정일이 있는 과거 사례"를 베이스라인
(d-130~d-31)/관찰구간(d-30~d+5)으로 나눠 **사후적으로** 리드타임을
측정하는 백테스트 구조였다. 실서비스는 "지정일"이 없다 — 매일 "오늘이
이상한 날인가"를 판정해야 한다. 그래서 새 함수가 필요하다(가칭
`scan_today`):

- 베이스라인 = 오늘 기준 **직전 100거래일**(날마다 굴러가는 롤링
  윈도우, 고정된 과거 구간이 아님)
- 판정 대상 = **오늘 하루 1개 포인트** — `ml_detector.build_features`로
  피처를 만들고, 베이스라인으로 학습한 `IsolationForest`가 오늘을
  이상치(-1)로 분류하는지만 본다
- `lead_time_days`/`false_positive_rate`처럼 지정일 기준으로 계산하던
  백테스트 전용 지표는 실서비스엔 없다 — 대신 "오늘 이상치로 판정된
  종목 수/비율"을 운영 모니터링 지표로 쓴다

`ml_detector.py`의 `run_case_ml`을 고치는 게 아니라(백테스트 검증용으로
계속 필요), 베이스라인/판정 로직을 공유 모듈로 뽑아서 `run_case_ml`과
`scan_today`가 같이 쓰는 구조로 가는 게 맞다 — 토이 프로젝트의 백테스트
능력을 잃지 않으면서 실서비스 로직을 추가하는 것.

## 성능 추정 (구현 전 추정치, 실측 필요)

- 200종목 x (베이스라인 130일 조회, 현재 페이지네이션 기준 약 2콜) ≈
  400콜. 호출 간 0.3~1초 간격을 감안하면 총 소요 대략 5~15분대로
  추정 — 장마감 후 여유 있게 끝날 걸로 보이나 실측 필요.
- IsolationForest 200회 재학습은 CPU로도 수 초~수십 초 수준, 병목
  아닐 것으로 예상.

## 남은 질문 (구현 시 확인)

- KIS "시가총액 상위" 순위조회의 정확한 엔드포인트/TR_ID (토이
  프로젝트에서 써본 적 없음 — Task 2 때처럼 실제 호출로 확인 필요)
- 200종목 순차 호출의 실제 소요 시간
- 베이스라인 100행 미달(`insufficient_data`) 종목이 실제로 전체의
  몇 %나 되는지 — 너무 많으면 `ML_BASELINE_LOOKBACK` 재검토 필요
